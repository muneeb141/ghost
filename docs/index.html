Ghost authentication

Anonymous identities and verified login for any Frappe business application. Ghost uses native User, OAuth Client and OAuth Bearer Token records and does not require ERPNext.

Security repair candidate — breaking API behavior.

This documentation describes the candidate, not a published Marketplace release. Existing integrations must follow the migration matrix. Read the actual verification results and remaining gates.

Setup

bench get-app https://github.com/muneeb141/ghost
bench --site your-site install-app ghost

Configure the OAuth Client and the anonymous Website User role in Ghost Settings before enabling Ghost Feature. For OTP login, configure an outgoing Email Account/template or SMS provider, explicitly enable OTP Login, and choose whether Public Signup is allowed. System User OTP login requires a separate opt-in; built-in users are excluded.

Google and magic-link conversion each have their own provider settings. The caller must still own the originating Ghost identity. Sandbox fixed codes work only inside automated tests.

API contracts

Frappe wraps return values in message. These authentication writes use POST.

Method under /api/method/Inputs and contract
ghost.api.ghost.create_ghost_sessionNo email; returns a fresh server identity and bearer credentials. A fingerprint cannot reconnect an account.
ghost.api.otp.send_otpExactly one email or phone and a purpose. Public response contains delivery status, never a code.
ghost.api.auth.loginDelivered Login OTP and exactly one email/mobile_no; native cookie session by default. Configured client_id opts into bearer issuance.
ghost.api.ghost.convert_to_real_userOriginating Ghost credentials, ghost_email, real_email and a Conversion otp_code. Caller verification bypass is rejected.
ghost.api.auth.refresh_bearer_tokenRefresh token; one-time rotation returns a replacement pair. Serialize concurrent refreshes.
ghost.api.social.convert_with_googleOriginating Ghost credentials, ghost_email and actual Google id_token. Checks audience and verified email.
ghost.api.magic_link.send_magic_linkOriginating Ghost credentials, ghost_email and real_email; no developer link in the response.
ghost.api.magic_link.consume_magic_linkOriginating Ghost credentials and emailed token; unrelated Guest browsers cannot consume the link.
ghost.api.lead.capture_emailOwned Ghost identity and captured email; a captured email alone does not prove ownership of another lead.
ghost.api.otp.validate_otpConsumes a recipient/purpose-bound OTP without logging in. Do not call it before login with the same code.

Sign Up and Reset Password are supported challenge purposes, but verifying them does not implicitly authenticate a user or reset a password. The consuming workflow must implement its own verified action.

Portal and headless clients

A same-origin portal can request a Login OTP and submit it directly to auth.login. Use native HttpOnly cookies, same-origin credentials and Frappe CSRF protection for authenticated writes. Cross-origin cookie clients require an explicit trusted origin and correct cookie deployment settings.

// Request a code, then submit the value actually delivered to the mailbox.
await fetch('/api/method/ghost.api.otp.send_otp', {
  method: 'POST', headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email, purpose: 'Login' })
});
await fetch('/api/method/ghost.api.auth.login', {
  method: 'POST', credentials: 'same-origin',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email, otp: deliveredCode })
});

The example assumes a Guest initial request. An already authenticated client must include its current Frappe CSRF token on writes. Headless applications use the issued bearer credentials and request replacement credentials explicitly with the configured client_id on login.

Anonymous creation returns bearer credentials, rather than automatically establishing an anonymous browser cookie. A magic-link consumer must carry the original application's credentials. The playground supports pasting the delivered link back into its original tab. A separate Guest tab cannot reconstruct that identity, and app-specific magic-link pages must preserve this requirement.

Data and the OTP name

The internal DocType remains OTP, with the table tabOTP and Python path ghost.ghost.doctype.otp.otp. No naming migration is part of this candidate. Guest resource access is removed; use the whitelisted API.

A future rename to Ghost OTP requires a versioned data migration and downstream updates to REST resources, SQL, custom scripts, reports and imports. A navigation label can change without renaming the internal DocType. See the separate rename plan.

New verified identities use native Frappe User rename, which updates native Link fields. Existing target users retain roles; only Ghost-owned references migrate automatically. Each consuming app owns its cart, booking, customer or other business-data migration policy.

Existing installations

Treat these changes as a major release. Back up and rehearse on a clone, inventory actual clients, update their contracts, run migration, configure explicit OTP/signup policy and verify the cutover before distribution. Native Frappe password login and User records are retained.

Caller-selected identities, verification bypass, fingerprint login and unverified automatic merging are removed intentionally. Legacy sandbox mode is disabled by normal migration. Previously affected credentials require a deliberate revocation plan; a code patch cannot identify all prior misuse or automatically undo earlier issuance.
